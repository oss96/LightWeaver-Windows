Advanced search: live updates

The owner asked: What is the cost of adding a live update with a reasonable interval, not every second? Maybe even indicate if an update happens. Maybe even the timer for the next update with a manual refresh. Today the page queries on first show and after a failure only; going Back keeps the old grid, so a title marked watched on the TV still shows as unplayed until a filter or the text changes.

Three ways the page could show it, from staying inside the system (A) to stretching it (C). All three sit on the same plumbing, described first, because the cost question is mostly answered there: the app already holds Jellyfin's session WebSocket, so most changes arrive by push and polling is only the fallback.

Shared plumbing (whichever option is picked)

  • Push first. UserDataChanged carries Played, IsFavorite, position and percentage per item, so a matching card is updated in place with zero requests. One re-query only when the change can move the item in or out of the results (the Watched filter is set, or the sort uses play data). LibraryChanged triggers one re-query per burst, debounced 3 s (a library scan sends many).
  • Only while seen. The page works only while it is the current page and the window is not minimized. Otherwise it sets a dirty flag, and on OnShown (Back) it re-queries once if dirty or older than 60 s.
  • Fallback poll. If the socket is down but the server answers, the page re-queries every 60 s, but only while it is visible and the window has focus. A reconnect triggers one catch-up query and stops the timer.
  • Server unreachable is already handled by the shell: ServerUnreachableView replaces the page, probes every 15 s with its own countdown, and Reload() re-queries when the server is back. The page draws nothing new for that case.
  • No flicker. Replace Items.Clear() + re-add in AdvancedSearchModel.RunAsync with a keyed diff (insert, remove, move, replace). An unchanged card keeps its decoded art (the keepPicture path in MediaCard.Item), and ScrollViewer anchoring keeps the first visible card fixed. Background updates never dim the grid. The 0.6 dim stays reserved for the user's own filter changes.

AStatus line and refresh buttonWithin the system

What changes: the header gets a quiet status after the count (“Live”, a short summary when something lands, or “Checked 1 min ago” when polling) and a Refresh button at the trailing end. Cards change in place and need no extra marking: the watched check or progress bar appearing is the indicator. Why: it answers “is this current?” where the eye already reads the count, and costs almost nothing. System impact: none new. The status dot reuses the 7 px LwOkBrush/LwOffBrush dot from the profile menu's server status (6 px here). Status text uses the existing Updating indicator's type (12, LwText3Brush), and the button is LwSubtleButton with Icons.Refresh.

BHeld changes: in place now, reflow on requestNew component variant · new rule

What changes: A's header, plus a split by kind. Changes that keep a card in place (watched check, progress, favourite) apply at once, and the card gets a brief 1 px accent ring. Changes that would move the grid (titles joining, leaving, re-sorting) wait while you are browsing. A floating pill counts them (“2 new · 1 leaving · Show”), and a leaving card stays in place, dimmed, with the reason under its title. At the top of the list, with the pointer off the grid, changes apply at once with no pill. Why: a live grid must never move under the pointer. This keeps the page honest about what changed without shifting what you are about to click. System impact: a new variant, the floating action pill. It uses the toast surface (LwPopupBrush, LwPopupBorderBrush, flyout shadow) in the 32 px stadium shape of the filter tokens, and sits top centre so it never meets the bottom-centre toasts. Two new card states: changed (1 px LwAccentFgBrush ring, the existing CurrentRing at 1 px, 1.5 s then a 200 ms fade) and leaving (art at 40 %). New rule: live updates never reflow a grid the user is browsing.

CSync control with history and a fallback countdownNew component · rule change

What changes: status and refresh merge into one stock SplitButton at the trailing end of the header. The main part refreshes; the chevron opens a short history of what changed (“14:32 · Glass Season marked watched · no longer matches”). Changed and new cards carry a 6 px accent dot before the title until hovered or until you leave the page. When the socket is down, the button shows a determinate ProgressRing that drains to the next check, labelled “Next check in 42 s”, the phrasing of the offline banner in design 14a. Why: this is the owner's “timer for the next update with a manual refresh”, shown only where a next update exists. In live mode nothing is scheduled; the next update comes whenever the server pushes one, so a countdown there would be made up. System impact: a new component (the sync control) from stock parts (SplitButton, ProgressRing, MenuFlyout surface), and a new card mark (title dot). Rule change: a visible 1 Hz countdown outside the offline banner, and an accent dot in the caption, which the system has kept to the art so far.

Recommendation: B

B is A plus the one thing A cannot do: it keeps the grid still while you browse. Push makes the cost near zero in all three, so the real choice is how the page moves. With the Watched filter set (the likely case for “what's left to watch?”), every title marked watched elsewhere leaves the results. In A that pulls cards out from under the pointer; in B it waits for a click. A countdown belongs only to fallback polling, and B (like A) states “Checked 1 min ago” there instead. If the owner wants the visible timer anyway, C's determinate ring can be added to B's Refresh button for fallback mode only. A is a sound first step if B's extra day is not worth it yet: B adds to A without changing anything A shipped.
